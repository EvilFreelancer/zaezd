# Tutu MCP, полный обзор сервера

Данные собраны 19 августа 2026 года прямыми вызовами к боевому эндпоинту. Всё, что ниже, проверено на живом сервере, а не пересказано из статей.

## Что это такое

`https://mcp.tutu.ru/mcp` - публичный MCP-сервер сервиса путешествий Туту. Туту заявляет себя первым российским онлайн-тревел-игроком, открывшим свои сервисы по этому протоколу. Сервер даёт поисковый слой над пятью продуктами Туту (отели, авиа, поезда РЖД, междугородние автобусы, электрички) плюс сборку ссылки на оплату.

Ключевое ограничение архитектуры сформулировано самим сервером в блоке `instructions`. Сервер read-only. Ни платежей, ни личных кабинетов, ни бронирований на стороне Туту он не делает. `create_checkout_link` - чистый построитель URL, корзину в своей сессии создаёт браузер пользователя, когда тот открывает ссылку. Это осознанное юридическое решение, о котором Туту писал на Хабре, персональные данные и согласия остаются на контролируемом сайте продавца.

## Технический паспорт

| Параметр | Значение |
|---|---|
| Эндпоинт | `https://mcp.tutu.ru/mcp` |
| Имя и версия | `tutu-mcp-server` `0.38.0` |
| Транспорт | streamable-http |
| Протокол по умолчанию | `2025-11-25` |
| Поддерживаемые версии протокола | `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` |
| Авторизация | не требуется для публичного поиска, сервер отвечает на анонимный POST |
| Capabilities | `tools`, `resources` (без подписки), `prompts`, `experimental` |
| `listChanged` | выключен на всех трёх |
| Инструментов | 16 |
| Ресурсов | 6 |
| Промптов | 1 |
| Фронт | Envoy, за ним uvicorn (Python, судя по ошибкам pydantic v2.12) |

Сервер различает клиента по методу и заголовку `Accept`. POST с JSON-RPC получает JSON-RPC, GET с `Accept: text/event-stream` получает SSE, GET с `Accept: text/html` получает HTML-лендинг на 83 КБ. Про лендинг Туту отдельно писал, до него люди из браузера видели `{"detail": "Method Not Allowed"}`.

Минимальный вызов, который работает прямо из терминала.

```bash
curl -sS -X POST https://mcp.tutu.ru/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

Заголовок `Accept` обязан содержать оба типа, иначе сервер ответит отказом. Сессию заводить не нужно, `Mcp-Session-Id` сервер не требует и не возвращает.

## Карта инструментов

Шестнадцать инструментов делятся на четыре группы.

Поиск, шесть штук.
- `search_hotels` - отели по городу и датам;
- `search_avia` - авиабилеты, город или конкретный аэропорт по названию либо IATA-коду, в одну сторону и туда-обратно;
- `search_rail` - поезда РЖД с реальными названиями вокзалов в каждом оффере;
- `search_bus` - междугородние автобусы;
- `search_etrain` - электрички;
- `search_multitransport` - веерный запрос по всем четырём транспортным режимам сразу с общей сортировкой по цене или времени.

Детализация, два инструмента.
- `get_offer_details` - карточка одного оффера, для отелей раскрывает номера и тарифы;
- `get_rail_seatmap` - схема вагонов выбранного поезда с геометрией мест.

Плейбуки, шесть инструментов вида `get_<domain>_instructions`. Это прогрессивное раскрытие, придуманное, чтобы не держать всю документацию в постоянном контексте. У каждого описание короче 460 символов, а внутри лежит подробный текст от 2,5 до 27 КБ.

Служебное, два инструмента.
- `create_checkout_link` - единая ручка чекаута для всех продуктов;
- `fetch_resource` - чтение любого ресурса `tutu://` как вызов инструмента, для клиентов, которые не показывают ресурсы сами.

Все шестнадцать помечены `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`. У поисковых и чекаутного `openWorldHint: true`, у плейбуков и `fetch_resource` он `false`.

## Ресурсы и промпты

| URI | Что внутри |
|---|---|
| `tutu://help/overview` | краткий индекс по серверу, дублирует блок instructions |
| `tutu://geo` | снимок словаря городов и точек с id, лёгкая замена live-подсказкам |
| `tutu://amenities/dictionary` | код удобства в русскую подпись, 6,4 КБ |
| `tutu://status` | здоровье сервера и апстримов, у зонда авиапоиска есть реальный `elapsed_ms` |
| `tutu://version` | сведения о сборке |
| `tutu://special-offers` | случайные демо-направления с рандомными датами, честно помечено как не живой прайс-фид |
| `tutu://debug/memory` | диагностика памяти процесса |

Промпт ровно один, `plan_trip`. Он оркестрирует `search_multitransport` плюс `search_hotels` под заданный бюджет, ждёт, что модель выберет самый дешёвый вариант проезда, а остаток отдаст под отель.

Ресурсы отдают иконки в формате MCP-иконок (svg и apple-touch-icon с CDN Туту), это редкая для российских серверов деталь.

## Двухшаговый поток и объект checkout_ref

Любой сценарий покупки на сервере устроен одинаково.

1. Вызов `search_*`, на выходе список офферов;
2. По желанию `get_offer_details` или `get_rail_seatmap` для одного-трёх офферов, которые пользователь реально сравнивает;
3. `create_checkout_link` с полями из `checkout_ref` выбранного оффера;
4. Пользователь открывает полученный URL, корзина создаётся в его браузерной сессии.

`checkout_ref` - это самодостаточный хэндофф-объект, который каждый оффер несёт с собой. Для поезда он выглядит так.

```json
{
  "transport": "railway",
  "departure_city_id": 2657260,
  "arrival_city_id": 2656873,
  "departure_station_code": "2000003",
  "arrival_station_code": "2060500",
  "train_number": "206Х",
  "departure_at": "2026-09-05T01:15:00+03:00",
  "offer_hash": "cf6757af54d6556d32647b07bf2fc993",
  "segment_hash": "d1d9827d4a868641860c5d0434f17f32",
  "search_id": "B1F18136-E24B-4B38-877A-6A07F67EE475",
  "result_id": "2a113da8-4ec3-5e46-a98c-eef925025e09",
  "card_id": "e5273202fc6756ff68194aa2d5a1821b"
}
```

Возвращаемый `kind` говорит, что именно получилось.

| `kind` | Смысл |
|---|---|
| `deeplink` | ссылка открывает страницу выбора мест или номера в сессии пользователя |
| `checkout_deeplink` | корзина уже с выбранными местами, работает в холодном браузере |
| `search_redirect` | дип-линк не собрался, это страница поиска, а не покупки |
| `order_url` / `seats_url` | запасной вариант с предзаполненной страницей заказа |

Различия по продуктам важны для интерфейса.
- Авиа отдаёт `mtp-deeplink`, который открывает корзину только из браузера с активной сессией Туту, холодный пользователь или вебвью Телеграма приземлится на поиск. Прямой round-trip дип-линкуется, если пробросить `is_round_trip` и `return_departure_at`, стыковочный round-trip откатывается в поиск;
- Поезд и автобус по умолчанию открывают выбор мест, а с подтверждённым выбором мест чеканят корзину, которая работает в холодном браузере;
- Отели по умолчанию открывают страницу отеля, а с `offerpack_hash` конкретного тарифа номера ведут сразу в корзину. Важная ловушка, `best_offer.offerpack_hash` из листинга корзину не чеканит, нужен хэш из `get_offer_details`;
- Электричка отдаёт просто URL расписания, покупки нет.

Отдельно про количество пассажиров. Если не пробросить `passengers_full/child/infant` из `checkout_ref`, Туту откроет корзину на одного взрослого и сумма не сойдётся с той, что показал агент.

## Форма ответов, что реально приходит

Проверено вызовами Москва - Казань на 5 сентября 2026 и Москва - Сочи на 10 сентября 2026.

Транспортный оффер несёт `offer_id`, `transport`, `price {amount, currency}`, `duration_min`, `carriers[]`, `search_results_url`, `checkout_url`, `departure_at`, `arrival_at`, `legs[].segments[]` с реальными названиями вокзалов и `geo_point_id`, `checkout_ref`, `details_ref`, `review_summary` и либо `variants[]` (авиа, автобус, электричка), либо сводку `fares` (поезд).

Сводка `fares` у поезда полезнее, чем кажется.

```json
"fares": {
  "count": 18, "price_from": 2090.93, "price_to": 7320.82, "currency": "RUB",
  "refundable_count": 18, "changeable_count": 0,
  "seat_categories": {
    "RESERVED_SEAT": {"count": 16, "price_from": 2090.93},
    "COMPARTMENT": {"count": 2, "price_from": 7320.82}
  }
}
```

Категория, отсутствующая в `seat_categories`, в продаже отсутствует, если только `uncategorized_fares` не говорит, что часть строк не удалось классифицировать. Нулевой счётчик исключает тариф, отсутствие счётчика - нет. Это тонкость, на которой агенты чаще всего врут.

Отель несёт `hotel_id`, `hotel_geo_id`, `name`, `stars`, `rating`, `review_count`, `address` в виде расстояния от центра, `location {lat, lng}`, `photos[]`, `alias`, `checkout_url`, `best_offer` и `photos_total`. Координаты в листинге есть у каждого отеля, это готовая карта без единого дополнительного запроса.

Цена отеля тегирована `price_basis: "stay_total"`. Это уже сумма за всё проживание и весь состав гостей. Умножать её на `stay.nights` нельзя, `nights` годится только чтобы подписать цифру.

Схема мест в поезде оказалась самым богатым источником для интерфейса.

```json
{"number": "1", "type": "LOWER", "group_index": 2, "compartment_number": 1,
 "deck": null, "gender": "NO_GENDER", "level": "bottom",
 "distance_to_nearest_wc_px": 95.5}
```

У вагона есть `canvas {width, height, svg_url, background_svg_url}` с контуром вагона на CDN Туту. Сервер честно предупреждает, что в SVG нет текстовых номеров мест, поэтому файл годится как подложка, а вся пространственная логика должна строиться на `seats[].position`. Поле `distance_to_nearest_wc_px` уже посчитано за вас, а `get_rail_seatmap` принимает `task` со значениями `together`, `far_from_wc`, `female`, `summary` вместо выкачивания всей карты.

## Пагинация, фильтры, режимы детализации

Пагинация общая для всех поисков. `page` от 1 до 10, `page_size` от 1 до 30 при десяти по умолчанию, перед следующей страницей надо смотреть `meta.has_more`.

Сортировка транспорта, `price_asc` по умолчанию, плюс `price_desc`, `duration_asc`, `departure_asc`. У `search_multitransport` вместо этого `optimize_for` со значениями `price` и `time`.

Серверные фильтры транспорта, `price_max`, `direct_only`, `carriers`. Важная деталь реализации, фильтр сначала вытягивает весь пул маршрута, потом фильтрует. Значит одним поиском возвращаются все совпадения, `meta.total_matched` показывает сколько их всего, а `has_more` остаётся честным. Ходить по страницам, чтобы собрать перевозчика, не нужно. Что именно выкинул фильтр, лежит в `meta.post_filter_dropped_*`.

Фильтровать по перевозчику наугад нельзя. Сначала читается `meta.carriers_available` со списком имён, числом офферов и ценой от, и фильтр строится эхом имени оттуда. Строка `aeroflot` не равна строке `Аэрофлот`.

Режим детализации `view` единый для всех читающих инструментов, `compact` по умолчанию и `full` по требованию. У отелей есть ещё `view='rules'` для точной лестницы отмены. Гарантия сервера сформулирована так, `full` никогда не добавляет факт, о существовании которого `compact` умолчал, он только разворачивает многословные блоки.

## Правила вывода, которые сервер требует соблюдать

Эти правила лежат в `instructions` и повторяются в плейбуках. Для хакатона они важны вдвойне, потому что судьи будут смотреть, насколько агент не врёт.

- Отзывы цитировать дословно, по одному-двум коротким фрагментам на плюс и минус, с датой в скобках, и называть охваченный диапазон дат;
- Никогда не выдумывать варианты, которых нет в текущем `hotels[]` или `offers[]`;
- Никогда не подменять отсутствующее поле веб-поиском или общими знаниями. Сервер прямо называет это крупнейшим режимом отказа в транскриптах агентов и предписывает говорить "Туту не вернул это поле в текущем ответе". Единственное исключение - IATA-коды;
- Останавливаться в названиях остановок автобуса, сырые id показывать нельзя;
- Всегда называть, какой населённый пункт и область были распознаны, поля `meta.from`, `meta.to`, `meta.resolved_geo`. Если пришёл `also_named[]`, значит был возможен омоним, надо назвать выбранный вариант и предложить поправить;
- Цены рендерить ровно как в пейлоаде, без округления;
- Ссылку `checkout_url` показывать рядом с выбранным вариантом, не дожидаясь вопроса, и воспроизводить символ в символ. Это непрозрачная строка, её нельзя перекодировать, обрезать параметры или подставлять id из другого места ответа. Отредактированная ссылка обычно всё равно открывается, поэтому "работает" не значит "ведёт на выбранный оффер";
- Эмодзи по одному на сущность, звезда для рейтинга, поезд, самолёт, автобус, электричка, плюс и минус для за и против, скрепка перед URL.

## Замеры производительности

Замеры сделаны последовательными вызовами с одной машины, каждый поиск прогонялся дважды.

| Инструмент | Холодный вызов | Повторный вызов | Размер ответа при `page_size=5` |
|---|---|---|---|
| `search_avia` | 2,0 с | 1,6 с | 24,2 КБ |
| `search_hotels` | 2,8 с | 1,7 с | 12,1 КБ |
| `search_rail` | 6,3 с | 1,6 с | 15,5 КБ |
| `search_multitransport` | 2,6 с | 1,6 с | 23,0 КБ |
| `get_rail_seatmap` | 2,7 с | - | 85,7 КБ в `compact` |

Видно, что сервер кэширует результаты поиска, повтор того же запроса стабильно укладывается в 1,6-1,7 с. Самый долгий холодный вызов у железной дороги.

Рейт-лимит на двенадцати быстрых подряд вызовах `fetch_resource` не сработал, все двенадцать вернули 200. Туту писал, что лимиты навешаны только на вызовы инструментов API, а лендинг и описания инструментов из-под них выведены, чтобы обновление страницы в браузере не выглядело атакой.

## Слабые места, они же точки для проекта

Здесь собрано то, что нашлось при разборе и что можно превратить в содержание хакатонного проекта.

**Манифест инструментов стоит около 25 тысяч токенов.** Суммарный объём описаний и JSON-схем всех шестнадцати инструментов - 102 143 символа. При грубой оценке в четыре символа на токен это примерно 25,5 тысяч токенов, которые уходят в каждый запрос к модели ещё до того, как пользователь что-то спросил. Распределение крайне неравномерное.

| Инструмент | Символов |
|---|---|
| `create_checkout_link` | 21 841 |
| `search_rail` | 15 902 |
| `search_avia` | 12 207 |
| `get_rail_seatmap` | 11 063 |
| `search_hotels` | 10 259 |
| `get_offer_details` | 9 007 |
| `search_multitransport` | 7 626 |
| `search_bus` | 6 379 |
| `search_etrain` | 4 977 |
| шесть плейбуков суммарно | 2 120 |

Туту оптимизировал ответы на 74 процента, о чём написал в статье, но сам манифест остался тяжёлым. Один `create_checkout_link` весит больше, чем все шесть поисков по отдельности. Это прямая заявка на трек оптимизации инструментов.

**Нет `outputSchema` и нет `structuredContent`.** Все ответы приходят как `content[0].text` со строкой JSON внутри. Клиенту приходится парсить строку, а модель не получает типовой контракт. Обёртка, которая объявит выходные схемы, сразу поднимет надёжность и снимет класс ошибок разбора.

**Нет UI-ресурсов.** В `resources/list` только данные `tutu://`, ни одного `ui://`, а у инструментов пустой `_meta`. Спецификация MCP Apps, принятая в январе 2026 совместно Anthropic, OpenAI и командой MCP-UI, позволяет инструменту вернуть и текст для модели, и указатель на интерактивный HTML для человека. Туту этого не делает, и это самая очевидная незанятая ниша.

**Геоданные только на уровне города для наземного транспорта.** Поезд, автобус и электричка не принимают вокзал на входе, хотя в ответе название вокзала есть. Авиа - исключение, принимает конкретный аэропорт. Для маршрутов вида "с Казанского вокзала" нужен собственный слой поверх.

**Мультитранспорт считает только взрослых.** Для компании с детьми надо руками расходиться по конкретным режимам.

**Часть полей регулярно приходит пустой.** В прогоне по Казани у отеля `room_size_sqm`, `breakfast_included`, `meal_name`, `pay_at_hotel`, `pay_online` были `null`, а `location.city` и `city_geo_id` пустые при заполненных координатах. Сервер требует честно говорить об отсутствии поля, и это создаёт ощутимую дыру в UX, которую можно закрыть внешними источниками, но только с явной пометкой источника.
