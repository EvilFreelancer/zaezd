# Архитектура, стек и план сдачи

Документ отвечает на три вопроса. Из чего собирать, как это устроить внутри, и что сдать, чтобы не потерять баллы на формальностях.

## Рекомендуемая архитектура, шлюз поверх Туту

Смысл конструкции в одном. Между моделью и `mcp.tutu.ru` ставится собственный MCP-сервер, который делает четыре вещи, которых нет у Туту.

```
Пользователь
    │
    ├── Claude / ChatGPT / VS Code ──┐
    │                                 │  MCP
    └── свой веб-клиент ─────────────┤
                                      ▼
                        ┌──────────────────────────┐
                        │   Шлюз (свой MCP-сервер) │
                        │                          │
                        │  ui:// ресурсы           │  MCP Apps, виджеты
                        │  outputSchema            │  типизированный вывод
                        │  свёрнутые инструменты   │  16 -> 4
                        │  кэш ответов             │  стабильность демо
                        └───────┬──────────┬───────┘
                                │          │
                    MCP ────────┘          └──────── HTTP
                     ▼                                ▼
            mcp.tutu.ru                    KudaGo, Open-Meteo,
            16 инструментов                isDayOff, Nominatim
```

Почему именно так, а не прямое подключение из фронтенда.

- Прямое подключение к Туту из браузера упирается в CORS и в то, что ключей нет, но и кэша нет тоже. Живой поиск занимает от 1,6 до 6,3 секунды, и на сцене это риск;
- Манифест Туту весит около 25,5 тысяч токенов. Прокси показывает модели свёрнутый набор и подгружает подробности по требованию, а не сразу;
- Ответы Туту приходят строкой JSON внутри текстового блока, без `outputSchema`. Прокси объявляет схемы и отдаёт `structuredContent`, и это снимает целый класс ошибок разбора;
- Виджеты MCP Apps можно отдавать только со своего сервера, у Туту ресурсов `ui://` нет.

Прокси-паттерн ещё и хорошо объясняется на одном слайде, а это прямо влияет на баллы за архитектуру.

## Стек

Стек не ограничен условиями, поэтому выбирать надо по скорости сборки и по тому, что читает ИИ-ревьюер.

| Слой | Выбор | Почему |
|---|---|---|
| Шлюз | TypeScript и официальный `@modelcontextprotocol/sdk` | один язык с фронтендом, MCP Apps ближе всего к TS-экосистеме |
| Альтернатива шлюзу | Python и официальный `mcp` SDK | если в команде сильнее Python, разница непринципиальна |
| Фронтенд виджетов | обычный HTML и немного ванильного JS либо Preact | виджет MCP Apps грузится в песочный iframe с жёстким CSP, тяжёлый бандл там мешает |
| Карта | MapLibre GL с тайлами OSM | без ключа, без вендора, координаты отелей уже приходят от Туту |
| Схема вагона | собственный SVG по данным `seats[]` | подложка Туту без номеров мест, рисовать надо самим |
| Кэш | файловый или SQLite | переживает перезапуск, годится как запись для офлайн-демо |
| Модель | любая с function calling | при коротком контексте сжатие манифеста обязательно |

Про модель отдельно. Если целитесь в локальную или в модель с окном 32K, манифест Туту съест почти всё. Туту сам писал, что проверял сервер на Qwen3-30B ровно поэтому.

## Кэш и запись, это одновременно стабильность и скорость

Три режима, переключаемые переменной окружения.

- `live` - всё идёт в Туту напрямую;
- `record` - идёт в Туту и складывает пары запрос-ответ на диск;
- `replay` - отвечает только из записи, в сеть не ходит.

Это даёт три выигрыша сразу. Разработка перестаёт ждать по две секунды на каждый вызов. Демо на сцене не зависит от вайфая площадки. И тот же набор записей превращается в фикстуры для тестов, а тесты ИИ-ревьюер засчитывает.

Ключ кэша строится из имени инструмента и нормализованных аргументов. Отдельно стоит помнить, что `search_id` в ответах Туту живёт недолго, поэтому воспроизведённая ссылка на чекаут может протухнуть. Для демо это неважно, для живого режима наблюдателя за ценой надо переискать, а не хранить ссылку.

## Что делать со временем ответа

Замеры с одной машины, каждый поиск дважды.

| Инструмент | Холодный | Повторный |
|---|---|---|
| `search_avia` | 2,0 с | 1,6 с |
| `search_hotels` | 2,8 с | 1,7 с |
| `search_rail` | 6,3 с | 1,6 с |
| `search_multitransport` | 2,6 с | 1,6 с |

Сервер кэширует, повтор стабильно укладывается в 1,6-1,7 секунды. Рейт-лимит на двенадцати быстрых вызовах подряд не сработал, значит параллелить веерные запросы можно.

Практика для интерфейса. Показывать промежуточное состояние с первой секунды, а не спиннер на шесть секунд. Прогревать типовые маршруты демо заранее. Если сценарий веерный, запускать все ветки параллельно и рисовать карточки по мере прихода.

## Структура репозитория под ИИ-проверку

Тридцать баллов из ста оценивает ИИ по документации, архитектуре и коду. Структура ниже написана под то, как машина читает репозиторий.

```
.
├── README.md                # что это, зачем, как запустить, как устроено
├── AGENTS.md                # соглашения проекта, карта репозитория
├── docs/
│   ├── user-guide.md        # пользовательская документация, сдаётся отдельной ссылкой
│   ├── architecture.md      # схема и потоки данных
│   ├── decisions.md         # принятые решения и обоснования
│   └── tutu-mcp-notes.md    # что выяснили про сервер Туту
├── src/
│   ├── gateway/             # MCP-шлюз, регистрация инструментов
│   ├── tutu/                # клиент Туту, типы, нормализация ответов
│   ├── ui/                  # ресурсы ui://, виджеты
│   └── enrich/              # внешние источники, погода, афиша, календарь
├── fixtures/                # записанные ответы для replay и тестов
├── tests/
└── .env.example
```

Что даёт баллы у машинного ревьюера.

- README, где первым делом сказано, что делает продукт и как его запустить одной командой;
- Файл решений, где каждое решение записано в форме "контекст, решение, следствие". Это прямое доказательство продуманности, которое ИИ распознаёт однозначно;
- Типы на границах. Ответы Туту нормализуются в собственные типы в одном месте, а не разбираются по всему коду;
- Тесты на нормализацию поверх записанных фикстур. Их немного, но они есть;
- `.env.example` вместо секретов в репозитории.

Что отнимает баллы.

- Расхождение документации и кода, машина сверяет это лучше человека;
- Мёртвый закомментированный код и заглушки с `TODO`;
- Один файл на две тысячи строк;
- README из трёх строк со ссылкой на демо.

## Питч на десять минут

Тайминги фасилитируются жёстко, невписавшихся останавливают. Судей трое, два технических и один продуктовый, значит говорить надо на два языка.

Разложение, которое обычно работает.

- Полминуты на проблему в одной фразе, без предыстории;
- Полторы минуты на то, почему существующий поиск на неё не отвечает, со ссылкой на конкретный факт про сервер, а не на общие слова;
- Четыре минуты живого прототипа. Это половина времени, и это правильно, потому что показывать надо на нём;
- Полторы минуты на архитектуру, один слайд со схемой, для технических судей;
- Минута на то, что измерили. Цифры до и после, число сценариев, время ответа;
- Минута на то, что дальше и почему это переживёт хакатон;
- Полминуты запаса, потому что тайминг жёсткий.

Первые тридцать секунд демо решают. Судья к вашему выступлению посмотрит два десятка проектов на том же сервере. Если на экране в этот момент переписка с ботом, вы неотличимы от предыдущих.
