# Композитор поездки

Ядро продукта. Оба ревьюера отдельно указали, что без детерминированного алгоритма сборки и код, и модель будут врать. Здесь он зафиксирован полностью.

## Вход и выход

```ts
type TripRequest = {
  topics: string[];        // темы confcal, слаги или названия
  origin: string;          // город человека
  budget?: number;         // рубли, необязательно
  dateFrom?: string;       // YYYY-MM-DD
  dateTo?: string;
  adults: number;          // по умолчанию 1
};

type TripResult = {
  event: EventCard;
  packages: TripPackage[];   // от одного до трёх
  coverage: CoverageNote;    // честная справка о покрытии каталога
  skipped: SkippedNote[];    // почему часть событий отброшена
};
```

## Шаг 1. Отбор событий

По теме "нейросети и ML" в каталоге 97 будущих событий. Строить транспорт и отели для всех нельзя.

Правила отбора, применяются по порядку.

1. Отбросить `format: "online"`, для них поездка не нужна. Они уходят в отдельный список "ехать никуда не надо" со ссылкой на событие;
2. Отбросить офлайн-события без города. Ехать некуда, транспорт и отели искать не по чему;
3. Отбросить события в городе отправления, туда ехать не надо. Тоже в отдельный список;
4. Отбросить события, которые выходят за `dateFrom` и `dateTo`;
5. Отбросить события, до которых уже не успеть. Проверяется не `start_date`, а день заезда из шага 2, потому что событие, открывающееся завтра утром, требует человека в городе уже сегодня, а отель на вчера не бронируется. Правило строже исходного и включает его в себя;
6. Отбросить события, у которых `end_date` раньше `start_date`. Такая запись противоречит сама себе, и одна испорченная строка каталога не должна ронять отбор целиком;
7. Отсортировать оставшиеся по близости даты, при равенстве по идентификатору каталога, иначе один и тот же каталог будет отвечать по-разному;
8. Взять максимум пять кандидатов;
9. Для первого кандидата построить полную поездку. Остальные четыре показать списком без расчёта, с кнопкой "посчитать".

Каждое отброшенное событие попадает в список с причиной и ссылкой, включая те, что не влезли в
пятёрку. Молча обрезанный список читается как "это всё, что есть", а это другое и неверное
утверждение.

Ограничение в одно рассчитанное событие на запрос - осознанное. Даже параллельно каждое событие стоит нескольких секунд, а веер по пяти событиям упрётся в спиннер.

## Шаг 2. Алгоритм дат

Самая недооценённая часть. Именно здесь появляется правильное число ночей и правильная полная цена.

```
событие: start_date, end_date, starts_at (может быть null)

день заезда:
  если starts_at известен и время начала < 12:00  → start_date минус 1 день
  если starts_at известен и время начала >= 12:00 → start_date
  если starts_at == null                          → start_date минус 1 день (осторожная оценка)

день выезда:
  end_date плюс 1 день, если событие заканчивается позже 18:00 или время окончания неизвестно
  иначе end_date

ночей = день выезда минус день заезда
```

**Времени окончания каталог не отдаёт.** Проверено на живой выдаче 19 августа 2026 года, событие содержит `start_date`, `end_date` и `starts_at`, поля времени окончания нет ни у одного события. Значит вторая ветка правила дня выезда на данных confcal недостижима, и день выезда это всегда `end_date` плюс один. Правило 18:00 остаётся в функции, потому что источник со временем окончания может появиться, и проверяется юнит-тестом, а не сценарием на фикстурах.

Ночей не может быть отрицательным. Ноль ночей означает однодневную поездку в соседний город, и тогда собирается вариант без отеля, но с обязательной обратной дорогой в тот же день. Насильно поднимать ноль до единицы нельзя, иначе продукт покупает ночь, которая человеку не нужна.

Даты заезда и выезда идут в `search_hotels` как `check_in` и `check_out`. Дата дороги туда - день заезда, дата дороги обратно - день выезда.

## Шаг 3. Транспорт туда и обратно

Обратная дорога обязательна. Оба ревьюера указали, что без неё итоговая цена заведомо неверна, а продукт обещает готовую поездку.

Два вызова `search_multitransport`, параллельно.

```
туда:    origin → event.city,  departure_date = день заезда
обратно: event.city → origin,  departure_date = день выезда
```

Мультитранспорт считает только взрослых. Для компании с детьми надо расходиться по конкретным режимам, в MVP этого нет и об этом написано в ограничениях.

Частичный отказ режима не означает его отсутствие. Пустой массив по одному режиму при живых остальных логируется, но не превращается в утверждение "самолётов нет".

## Шаг 4. Проверка выполнимости

Применяется к каждой паре "дорога туда, дорога обратно".

| Проверка | Правило | Что делает |
|---|---|---|
| Успевает к открытию | `arrival_at` не позже `starts_at` минус 60 минут | иначе вариант помечается красным и не может быть основным |
| Уезжает после окончания | отправление обратно не раньше окончания события | иначе помечается |
| Время неизвестно | `starts_at == null` | проверка ослабляется, на карточке подпись, что время начала каталог не отдал |
| Время не прочиталось | строка есть, но это не момент времени | то же, что отсутствие, вариант не может быть основным |
| Времени нет вовсе | прибытие или отправление обратно не передали | вариант не может быть основным, незнание это не то же самое, что успевание |

Все сравнения идут по моментам времени, а не по округлённым минутам. Запас в 59 минут 30 секунд
округляется до 60 и при наивной реализации проходит проверку, которая существует ровно для этого
случая. Смещение в отметке времени обязательно, потому что `Date.parse` без него читает время в
часовом поясе машины, и одна и та же поездка оказывалась бы выполнимой на сервере в Москве и
невыполнимой на сервере в Токио.

Запас до начала показывается числом. Не "успевает", а "запас 4 ч 15 мин".

## Шаг 5. Отели

Tutu не ищет по координатам, только по городу. Поэтому.

1. `search_hotels` по `city_name` события, даты из шага 2, `page_size` 20-30;
2. Если площадка геокодирована точно, посчитать расстояние по прямой от каждого отеля до неё, координаты у отелей есть в листинге;
3. Отсортировать по расстоянию, взять три ближайших в разумной ценовой вилке;
4. Для победившего отеля посчитать время пешком через OSRM;
5. Если площадка геокодирована неточно, сортировать по цене и рейтингу, а блок расстояния не показывать вовсе.

Гостиничный `geo_id` берётся только из ответа `search_hotels`, никогда из транспортного ответа.

Цена отеля - `stay_total`, за всё проживание. В сумму она входит как есть.

## Шаг 6. Сборка трёх пакетов

Из декартова произведения "дорога туда × дорога обратно × отель" отбираются три варианта по трём правилам. Считается только по вариантам, прошедшим проверку выполнимости.

```
полная цена = дорога туда + дорога обратно + отель + цена события (если разобралась)

пакет "Дешевле всего"  = min(полная цена)
пакет "Без отпуска"    = min(число сгорающих рабочих дней), при равенстве min(полная цена)
пакет "Быстрее всего"  = min(duration_min туда + duration_min обратно)
```

Множество сужается по очереди. Сначала остаются варианты, прошедшие проверку выполнимости, затем
те, что влезают в бюджет, и только к остатку применяются три правила. Если сужение опустошило
множество, оно отменяется и добавляется предупреждение, потому что помеченный экран лучше пустого.

Каждая ничья доводится до идентификатора варианта. Цена, потом длительность, потом идентификатор,
и порядок никогда не решается тем, в каком порядке источник вернул варианты.

Если два правила выбрали один и тот же вариант, показывается меньше карточек, а не дубликаты. Если
ни один вариант не влезает в бюджет, показывается ровно одна карточка, лучшая по цене, с плашкой
превышения. Три варианта, которые человек не может себе позволить тремя разными способами, это не
ответ. Пустой экран недопустим.

## Шаг 7. Цена во времени

```
сгорающие рабочие дни = число дней в диапазоне
                        [календарный день отправления туда,
                         календарный день прибытия обратно],
                        которые isDayOff считает рабочими
                        и в которые человек находится в отъезде
                        или в дороге в рабочее окно 10:00-19:00
ночей вне дома        = число ночей из шага 2
запас до начала       = starts_at минус arrival_at
```

Диапазон берётся по фактическим дорогам, а не по интервалу проживания, и это принципиально. Если считать по интервалу проживания, число рабочих дней одинаково у всех вариантов, правило "Без отпуска" падает в ничью и вырождается в копию "Дешевле всего". По фактическим дорогам правило начинает различать варианты. Ночной поезд, уходящий в 23:15 в пятницу, пятницу не жжёт, потому что рабочее окно человек отработал. Дневной рейс в 14:00 ту же пятницу жжёт.

## Шаг 8. Чекаут

Ссылка на оплату не одна. Их две-три, и это надо показать чек-листом, а не одной кнопкой.

| Компонент | Как собирается | Что откроется |
|---|---|---|
| Дорога туда | `create_checkout_link` с `checkout_ref` | зависит от `kind` |
| Дорога обратно | то же | зависит от `kind` |
| Отель | `get_offer_details`, затем `create_checkout_link` с `offerpack_hash` тарифа номера | корзина |
| Отель без деталей | `create_checkout_link` с `checkout_ref` листинга | страница отеля, не корзина |

Подпись кнопки берётся из фактического `kind`, а не назначается заранее.

| `kind` | Подпись |
|---|---|
| `checkout_deeplink` | Открыть корзину |
| `deeplink` | Открыть страницу выбора |
| `hotel_page` | Открыть страницу отеля |
| `search_redirect` | Открыть поиск, корзины не будет |
| `order_url` | Открыть заказ |
| `seats_url` | Выбрать места |
| ничего или незнакомое значение | Открыть на Туту, с пометкой, что Туту не сказал, что откроется |

`hotel_page` приходит, когда в `checkout_ref` не оказалось `hotel_alias`, и это отдельный вид
ссылки, а не разновидность `deeplink`. `seats_url` подписывается по действию, а не по объекту,
потому что человек на этой странице выбирает места, и правило `web-ui` называет кнопку так же.
Неизвестный вид получает самую осторожную формулировку и никогда не получает слово "корзина",
иначе новый вид ссылки у Туту задним числом превратит страницу в корзину.

Отдельно про авиа. `mtp-deeplink` открывает корзину только из браузера с активной сессией Туту. Судья откроет ссылку в инкогнито и попадёт на поиск. Поэтому по умолчанию в демо ведёт поезд плюс отель, а авиа показывается как альтернатива с явной подписью.

Без `passengers_full/child/infant` из `checkout_ref` корзина откроется на одного взрослого, и сумма разъедется с карточкой. Эти поля пробрасываются всегда.

## Бюджеты времени на оркестрацию

Последовательность вызовов и их стоимость по замерам.

| Шаг | Вызовов | Секунд |
|---|---|---|
| справочники confcal | 2, кэшируются на весь процесс | 0,5 |
| поиск событий | 1 | 0,5 |
| геокодинг площадки | 1, кэшируется | 1,5 |
| транспорт туда и обратно | 2, параллельно | 2,6 |
| отели | 1 | 2,8 |
| OSRM | 1 | 1,2 |
| календарь и погода | 2, параллельно, необязательные | 2,1 |

Суммарно при полном параллелизме около 5-6 секунд на холодную, 2-3 на повторную. Это укладывается в приличное время, но только при условии, что карточки стримятся по мере готовности, а не ждут последнего ответа.

## Что композитор не делает

- Не строит поездку для онлайн-событий;
- Не рисует точную метку, если площадка не геокодирована;
- Не умножает цену отеля на число ночей;
- Не считает пустой массив режима доказательством отсутствия транспорта;
- Не включает в сумму цену события, если она не разобралась в число;
- Не называет корзиной то, что по `kind` корзиной не является.
